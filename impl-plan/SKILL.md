# 実装計画書の作成

既存のドキュメント（要件定義書、企画書、仕様書など）を読み込み、アジャイル方式の実装計画書を Markdown ファイルとして出力する。

## 手順

### 1. 入力ドキュメントの確認

以下を確認する:

- **参照するドキュメント**: 指定されたパスをすべて読み込む。複数可。指定がなく、ワークスペースから安全に特定できない場合はユーザーに確認する。
- **出力先**: プロジェクト構成を見て適切な保存先（例: `docs/implementation-plan.md`）を判断する。既存ファイルの上書きや、複数の有力候補がある場合はユーザーに確認する。

### 2. ドキュメントの分析

読み込んだドキュメントから以下を抽出する:

- プロダクトの目的・ゴール
- 機能要件の一覧
- 非機能要件（あれば）
- 技術的な制約・前提条件
- 既存システムとの連携（あれば）

### 3. イテレーション設計

以下の原則に従ってイテレーションを設計する:

#### 核心原則: 動くものを積み重ねる

- **ウォーターフォール禁止**: 「まず全体の基盤を作り、次に全機能を載せる」ではなく、「小さく動くものを作り、機能を足していく」方式で計画する。
- **各イテレーション終了時に視覚的に確認できる成果物があること**: これは必須条件。画面、出力、動作する UI など、目で見て「動いている」と分かるものを含める。
- **成果物は確認用の一時的なものでもよい**: 最終形でなくてよい。ハードコードされた値を表示するだけ、モックデータで動くだけでも構わない。後のイテレーションで本物に差し替える。
- **機能ごとの縦割りで進める**: レイヤーごと（横割り）ではなく、機能ごと（縦割り）に実装する。例えば「まず DB 層を全部作り、次に API 層を全部作り…」ではなく、「機能 A に必要な DB・API・UI をまとめて作る」方式で進める。
- **イテレーションはなるべく細分化する**: 大きな機能は複数イテレーションに分割する。「1イテレーション = 1つの確認可能な進捗」を目指す。
- **コンポーネントの用意は実際に必要になるまで遅らせる**: 「将来使うから先に作っておく」は禁止。管理クラス・基盤システム・抽象化レイヤーなどは、それを使う機能を実装するイテレーションで初めて導入する。例: 画面遷移管理は複数画面が実際に必要になるイテレーションで作る。サウンドマネージャーはサウンドを組み込むイテレーションで作る。あるイテレーションのタスクに「〇〇の骨格を用意」「〇〇管理の基礎」のような項目が含まれていたら、それが本当にそのイテレーションで使われるか再確認する。
- **すべての完了条件は機械検証可能にする**: 人間の確認を完了条件にしない。「目で見て確認」のみで完了とする項目を作らない。視覚成果物がある場合でも、必ずエージェントが exit code・ログ・スナップショット・HTTP レスポンス・画像のマルチモーダル直接確認などで pass/fail を判定できる手段を併設する。これがないとエージェントは自走できない。

#### 設計の進め方

1. 機能要件をユーザーストーリーまたは機能単位に分解する。
2. 依存関係を整理する。
3. 以下の順でイテレーションを組み立てる:
   - **最初のイテレーション**: 最小限の動作する画面または出力。技術スタック確認も兼ねる。
   - **以降のイテレーション**: 機能を1つずつ追加し、毎回「見て確認できる」状態にする。
   - **後半のイテレーション**: 仕上げ（エラー処理、バリデーション、UI 調整など）。
4. 各イテレーションに **検証項目**（必須・1つ以上）を記載する。人間の確認を挟まず、すべてエージェントが非干渉な検証で pass/fail を判定できるものにする:
   - 各項目に **実行コマンド** と **判定基準**（exit code 0 / 特定文字列の存在 / ファイル生成 / スナップショット一致 / 画像のマルチモーダル確認結果など）を必ず明記する。
   - `verify`のexit 0はそのイテレーションの検証完了を示す。**イテレーション完了 = タスク完了 + `verify`のexit 0** とし、ユーザーの報告待ちを完了条件にしない。
   - 自動検証できない確認は検証項目として書かない。まず自動検証可能な経路（ヘッドレス実行、プロセス内API、バッチモードなど）へ設計し直すことを検討し、それでも不可能なものだけを計画書末尾の「自動検証対象外（既知の制約）」に理由付きで記録し、完了条件から外す。

### 4. テストハーネス設計（自走対応）

エージェントが人間の介入なしに各イテレーションを判定できる検証基盤を計画書に含める。具体ツール（Playwright / pytest / Vitest など）には依存せず、対象プロジェクトに合わせて以下の観点を計画書に書き起こす:

- **非干渉性の目的**: OS APIを一律に禁止するのではなく、同じコンピュータ上のユーザー作業を妨げないことを目的とする。自動E2EではOSレベルの入力取得・注入、フォーカスや前面ウィンドウの奪取、可視ウィンドウの表示・移動・リサイズ、実デスクトップや他アプリを含むキャプチャ、実スピーカー・マイク等を使用しない。ヘッドレス・オフスクリーン実行、プロセス内API、隔離した仮想デバイス、固定パスへ出力する観測物を使う。非可視・非アクティブでユーザー資源へ影響しないプラットフォーム初期化は許容できる。
- **非干渉手段の逸脱禁止**: `osascript`、System Events、`screencapture`等による前面化、ウィンドウ操作、入力注入、デスクトップキャプチャを検証手段に使わない。これらでしか確認できない項目は検証項目にせず、自動検証対象外として記録する。
- **統一エントリポイント**: `setup` / `run` / `verify` の3コマンドだけで全自動検証が走るようにする。`verify`の **exit 0 = 全検証項目の完了** と定義する。
- **判定の一意性**: すべての検証は exit code、または grep 可能な構造化ログ（JSON Lines 推奨）で pass/fail が機械的に決まるようにする。
- **再現性の確保**: 乱数シード固定、時刻のモック、外部依存（ネットワーク・DB・LLM など）のスタブ化方針を示す。
- **観測手段**: 標準出力・構造化ログ・スクリーンショット/スナップショット・HTTP 応答・画像のマルチモーダル直接確認のうち何を採用するか明記する。
- **非干渉性の構造的保証**: 非干渉性はまず構造で担保する。ヘッドレス/オフスクリーン指定を起動経路に固定する、キャプチャ元をレンダラのオフスクリーンターゲットに限定する、OS入力・デスクトップキャプチャ系APIを依存に含めない、の3点をハーネス設計の前提として計画書に書く。
- **非干渉性の実行時検証**: 非干渉性がソースコードではなく起動時に解決される環境状態（env var、ディスプレイサーバの有無、nullドライバの実在、プラットフォームのヘッドレス対応）に依存する場合にのみ計画する。依存しない場合（プロセス内API・HTTP応答・標準出力だけで判定するテストなど）は構造的保証のみでよく、メタデータの記録を要求しない。
  - **検証はハーネス起動時に1回**行い、そこでpass/failを確定させる。各イテレーションの検証項目では再掲せず、自分の判定基準だけを書く。
  - **設定値のエコーバックを禁止する**。自分が渡した値をログに書き出して自分で検証しても、env varによる上書き（例: `PWDEBUG=1`がheadless指定を無効化する）を検出できない。ランタイムAPIに解決後の状態を問い直して記録する（例: Godotでは`DisplayServer.get_name()`が`headless`を返すこと）。
  - **読み戻しAPIがないスタックでは環境前提を検証する**（例: `DISPLAY`と`WAYLAND_DISPLAY`がいずれも未設定、またはXvfbのDISPLAY番号であること）。一律に読み戻しを要求しない。
  - **記録対象はそのプロジェクトが実際に使うサブシステムだけ**に絞る。目安として、画面を持たないCLIは0項目、UI E2Eはディスプレイ方式とキャプチャ元の2項目、音を出すなら音声出力先を足して3項目。
  - **fail条件は違反のみ**とする。解決後の状態が期待値と異なることをfailとし、メタデータの欠落自体はfailにしない。欠落は計装の不足であり干渉の証拠ではない。
  - **構造上ヘッドレス化できない対象は監視しない**。GUIアプリのEditorを経由するテスト（例: UnityのEditMode/PlayModeテスト）などは実行時検証の対象にしない。まずEditorを経由しない検証経路（バッチモード、プロセス内API）へ設計し直すことを優先し、それでも不可能なら自動検証対象外として記録し、完了条件に含めない。
- **UI/視覚成果物の機械化**: 画面確認は以下のいずれか1つ以上を必ず計画する。
  - 隔離したテストプロセスがスクリーンショットを固定パスに出力し、Codexが画像を直接確認して「期待される表示状態」と一致するか判定する（ゴールデンが未整備でも初回から運用可能）。デスクトップ、他アプリ、ユーザーの作業内容を含む画像は使用しない。
  - スクリーンショット + ゴールデン画像比較（pixelmatch など）。
  - DOM / テキスト / アクセシビリティツリーへのアサーション。
  - 動画/GIF キャプチャをフレーム分解してマルチモーダル確認。
- **マルチモーダル確認の判定基準明記**: 「〇〇ボタンが赤色で中央に表示」「エラーメッセージが日本語で表示」など、何が映っていれば pass かを計画書に書く。
- **観測物の保存先**: ログ・スクリーンショット・スナップショットを固定パスに揃え、失敗時に何を見れば原因が分かるか明記する。
- **権限昇格時の判断**: WindowServer、Accessibility、画面収録、入力監視等の権限を要求する前に非干渉性を確認する。前面化、ウィンドウ操作、入力注入、デスクトップキャプチャが必要なら自動検証を停止し、自動検証対象外として記録する。サンドボックス失敗だけを理由に禁止操作へ切り替えない。

### 5. 計画書の出力

[template.md](template.md) のテンプレートに従って計画書を作成し、指定パスに保存する。

### 6. 確認

出力後、ユーザーに以下を伝える:

- 計画書の保存先パス
- 全体のイテレーション数と概要
- `verify`が判定する検証範囲と、自動検証対象外として残した項目（あれば）
