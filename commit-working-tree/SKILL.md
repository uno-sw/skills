# ワーキングツリーのコミット

現在の Git ワーキングツリー全体を、安全性とリポジトリ固有の規約を確認したうえで1つのローカルコミットにする。

このスキルの呼び出しは、対象リポジトリで `git add -A` と通常の `git commit` を実行する承認を含む。push、amend、履歴改変、強制操作への承認は含まない。

## 1. リポジトリと変更を確認する

コミット操作の前に、以下を確認する。

- リポジトリのルートと、適用対象となる `AGENTS.md` などの指示
- branch、upstream、ワーキングツリーと index の状態
- staged、unstaged、削除、未追跡ファイルを含む差分と統計
- 最近のコミットログに見られるメッセージ規約
- merge、rebase、cherry-pick、revert、bisect の進行状態と未解決コンフリクト

差分は内容まで読み、ファイル名と統計だけでコミット内容を判断しない。未追跡ファイルも、コミット対象として妥当か確認する。

次の場合はコミットせず、判明した状態を報告する。

- コミット対象の変更がない
- 未解決コンフリクトがある
- merge や rebase などが進行中で、依頼がその操作の完了を明確に意図していない
- 現在地から対象リポジトリを安全に一意特定できない

## 2. 疑わしい対象で停止する

秘密情報や誤追加の可能性を確認する。たとえば認証情報、秘密鍵、トークンを含み得る設定、環境ファイル、巨大な生成物、意図不明なバイナリである。

疑わしい対象があれば、勝手に除外も追加もせず、ファイル名と懸念理由を示してユーザーの判断を待つ。秘密値そのものは出力しない。通常のソースコード中に秘密情報らしい文字列が見つかった場合も同様に停止する。

## 3. コミット前に検証する

`AGENTS.md`、プロジェクト設定、既存の開発用コマンドから、変更に関連する必須または標準的なテスト、lint、型検査、ビルドを特定して実行する。

- 変更範囲に比例した検証を選ぶ。
- formatter や lint の自動修正など、ファイルを書き換えるコマンドは、リポジトリ指示で明確に必要な場合またはユーザーが依頼した場合に限る。
- 検証が失敗したらコミットせず、失敗したコマンドと要点を報告する。
- 実行すべき検証を特定できない場合は、実行していないことを明示して続行できる。

## 4. 全変更をステージして最終確認する

安全確認と検証を通過したら `git add -A` を実行する。これは ignored ファイルを除き、追跡済み変更、削除、未追跡ファイル、および既に staged の変更をすべて対象にする。

その後、`git diff --cached --check`、cached diff、統計、status を確認する。空のコミットは作らない。ステージ後に意図しない内容や疑わしい対象が判明した場合はコミットせず停止し、index を勝手に巻き戻さない。

## 5. コミットメッセージを決める

最近のコミットログから、言語、接頭辞、scope、文体の一貫した規約が認められる場合はそれに従い、実際の staged diff 全体を簡潔かつ具体的に要約する。

履歴が少ない、複数の規約が競合する、または一貫した規約を判断できない場合は、差分に合う候補を提示してユーザーに選択または修正を求める。曖昧な規約を推測してコミットしない。

## 6. コミットして結果を確認する

通常の `git commit` を実行し、Git hooks と既存の署名設定を尊重する。`--no-verify`、`--amend`、強制オプションは使用しない。

成功後に以下を確認して報告する。

- commit hash と件名
- コミットされた変更の概要
- 実行した検証と結果
- コミット後の status と残存変更
- push していないこと

コミットまたは hook が失敗した場合は、再試行や index の巻き戻しを勝手に行わない。失敗理由、現在の staged/unstaged 状態、ユーザーが判断できる再開方法を報告する。hook がファイルを書き換えた場合や、成功後に変更が残った場合も明示する。
